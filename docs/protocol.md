# Protocol reference

This document is normative for the code in `firmware/`. If a constant here
disagrees with the source, the source wins; the tables below are generated by
reading the headers and are kept in sync manually.

- Flash partitions: `firmware/common/include/flash_layout.h`
- Frame format: `firmware/common/include/ota_protocol.h`
- Metadata layout: `firmware/common/include/ota_metadata.h`
- Persisted records: `firmware/common/include/record_store.h`,
  `firmware/common/include/config_store.h`
- Pinout and timing: `firmware/app/include/app_config.h`
- AT parsing: `firmware/common/src/esp_at_parser.c`
- GATT setup: `firmware/app/src/services/ble_service.c`

## 1. Physical links

| Link | Instance | Pins | Settings | Peer |
| --- | --- | --- | --- | --- |
| Co-processor | USART1 | PA9 TX, PA10 RX, AF7 | 115200 8N1 | ESP32 running ESP-AT |
| PC test link | USART2 | PA2 TX, PA3 RX, AF7 | 115200 8N1 | ST-LINK virtual COM port |
| Sensor | I2C1 | PB6 SCL, PB7 SDA, AF4 | 100 kHz | SHT30 at 0x44 |
| Light sensor | ADC1_IN0 | PA0 analog | 12-bit | divider / photoresistor |
| LED | GPIOA | PA5 | push-pull | Nucleo LD2 |
| User button | GPIOC | PC13 | input, pull-up | Nucleo B1 |

USART2 carries a byte stream that is demultiplexed by
`firmware/app/src/app/host_link.c`:

- a line terminated by `LF` (a bare `CR` is ignored) is a JSON command/response,
- a byte pair `A5 5A` switches the link to binary frame mode,
- after one complete frame the link returns to text mode and resynchronises on
  the next `A5 5A`.

## 2. JSON control messages

Field extraction is flat-object only (`mini_json.c`): keys at the top level,
string/integer/boolean values. Nested objects are skipped while searching for a
key.

Host to device:

| Message | Example | Device action |
| --- | --- | --- |
| info | `{"cmd":"info"}` | sends an `info` reply |
| wifi.set | `{"cmd":"wifi.set","ssid":"MyNet","password":"secret"}` | `AT+CWJAP`, then persists credentials |
| wifi.clear | `{"cmd":"wifi.clear"}` | `AT+CWQAP`, erases the config record |
| wifi.status | `{"cmd":"wifi.status"}` | reports SSID, IP and provisioning state |

`password` and `pass` are both accepted. Credentials are validated before they
reach flash or the AT parser: SSID is 1–32 bytes, password is 0–64 bytes, both
must be printable ASCII, and `"`, `\`, `CR`, `LF` and other control characters
are rejected (they would break `AT+CWJAP="ssid","pass"`).

Device to host:

| Message | Example |
| --- | --- |
| info | `{"type":"info","name":"stm-ble-ota","version":"0.2.0","version_raw":512,"hardware_id":80,"ota_state":0,"last_reason":0,"fault_count":0,"last_err":0,"last_err_name":"OK","ble_connected":false,"wifi_connected":false}` |
| wifi | `{"type":"wifi","ok":true,"connected":true,"ssid":"MyNet","ip":"192.168.1.42","provisioned":true}` |
| wifi error | `{"type":"wifi","ok":false,"error":"wifi connection failed"}` |
| sensor | `{"type":"sensor","valid":7,"uptime_ms":12345,"temperature_centi":2412,"humidity_centi":5120,"light_mv":1870}` |
| ota progress | `{"type":"ota","state":1,"reason":0,"received":512,"total":18072}` |
| error | `{"type":"error","message":"unknown command"}` |

`valid` bit 0 = temperature, bit 1 = humidity, bit 2 = light. The same sensor
sample is also published as a 20-byte binary notification on the BLE sensor
characteristic (see `sensor_notify_payload_t` in `ota_protocol.h`).

`reason` is the 8-bit `ota_reason_t` value carried in OTA progress/info
payloads. The CLI `ota status` command additionally reports the same failure
translated into the device-wide 16-bit space as `err_code` / `err_name`; the
full table is in [error_codes.md](error_codes.md).

## 3. ESP-AT command sequences

### 3.1 Boot and WiFi provisioning

```
MCU                                ESP32 (ESP-AT)
 |  AT                              |
 | -------------------------------> |
 | <----------------------------- OK|
 |  ATE0                            |
 | -------------------------------> |
 | <----------------------------- OK|
 |  AT+CWMODE=1                     |
 | -------------------------------> |
 | <----------------------------- OK|
 |  AT+CWAUTOCONN=1                 |
 | -------------------------------> |
 | <----------------------------- OK|
```

Provisioning (issued by `wifi.set`):

```
 |  AT+CWJAP="<ssid>","<pass>"      |   timeout 20 s
 | -------------------------------> |
 | <------------------------- WIFI CONNECTED   (URC)
 | <------------------------- WIFI GOT IP      (URC)
 | <----------------------------- OK|
 |  AT+CIPSTA?                      |   only for wifi.status
 | -------------------------------> |
 | <---- +CIPSTA:ip:"192.168.1.42"  |
```

`wifi.clear` issues `AT+CWQAP` and erases both config pages. Boot reconnect is
attempted by `wifi_service_tick()` every 30 s while the stored config is marked
provisioned and auto-connect, until `WIFI GOT IP` is seen.

URC handling: `WIFI CONNECTED` and `WIFI GOT IP` set the connected flag;
`WIFI DISCONNECT` clears it. `+WRITE:` URCs are only delivered when the ESP-AT
firmware has BLE GATT server mode enabled.

### 3.2 BLE server setup

```
AT+BLEINIT=2
AT+BLENAME="STM-BLE-OTA"
AT+BLEGATTSSRVCRE
AT+BLEGATTSSRVSTART
AT+BLEADVPARAM=50,150,0,0,7,0,0,0
AT+BLEADVDATA="020106030300FF"
AT+BLEADVSTART
```

The advertising payload is: `02 01 06` (flags, LE general discoverable),
`03 03 00 FF` (complete list of 16-bit service UUIDs, `0xFF00` little-endian).

Note: ESP-AT's `gatts_data.csv` custom-service path supports 16-bit UUIDs.
The profile therefore uses the unassigned `0xFF00` range. A 128-bit UUID
profile would require modifying ESP-AT itself; see
`docs/esp32_at_custom_service.md`.

Notification (each AT command carries at most 20 payload bytes):

```
AT+BLEGATTSNTFY=<conn>,1,<char>,<len>
>
<len raw bytes>
OK
```

Writes from a central arrive as:

```
+WRITE:<conn>,<srv>,<char>,<len>,<hex data>
+WRITE:<conn>,<srv>,<char>,<desc>,<len>,<hex data>
```

Connection events: `+BLECONN:<conn>,<addr>` and `+BLEDISCONN:<conn>,<addr>`.

## 4. GATT profile

Service index 1 in the ESP-AT service table, 16-bit UUID `0xFF00`
(unassigned range; standard base UUID form
`0000ff00-0000-1000-8000-00805f9b34fb`).

| Char index | UUID | Direction | Payload |
| --- | --- | --- | --- |
| 0 | `0xFF01` info | read, notify | JSON `info` message |
| 1 | `0xFF02` sensor | notify | 20-byte `sensor_notify_payload_t` |
| 2 | `0xFF03` provisioning | write, notify | JSON `wifi.set/clear/status`; replies are JSON |
| 3 | `0xFF04` OTA control | write, notify | binary frames: BEGIN/END/ABORT; progress and result frames |
| 4 | `0xFF05` OTA data | write | binary frames: DATA |

Characteristics 3 and 4 feed the same OTA frame parser, so a peer may send all
frames on either characteristic; the reference host tool uses 3 for control and
4 for bulk data.

Because ESP-AT fragments notifications at 20 bytes, a receiver must reassemble
both JSON and binary frames. `tools/ota_host.py` contains reference
implementations (`JsonAssembler`, `FrameAssembler`).

## 5. OTA frame format

Every frame is a 16-byte header followed by `payload_len` bytes, `payload_len`
in 0..512.

| Offset | Size | Field | Notes |
| --- | --- | --- | --- |
| 0 | 2 | sync | `0xA5 0x5A` |
| 2 | 1 | type | see below |
| 3 | 1 | flags | must be 0 |
| 4 | 2 | seq | sender's counter, wraps at 65535 |
| 6 | 2 | payload_len | 0..512 |
| 8 | 4 | offset | byte offset in the image, DATA only |
| 12 | 4 | payload_crc32 | CRC-32/IEEE (reflected `0xEDB88320`), init `0xFFFFFFFF`, xorout `0xFFFFFFFF` |
| 16 | N | payload | |

CRC-32 is `zlib.crc32` in Python and `crc32_ieee_buf()` in C.

### 5.1 Frame types

| Type | Value | Direction | Payload |
| --- | --- | --- | --- |
| CMD_JSON | 0x01 | host → device | JSON text |
| ACK_JSON | 0x02 | device → host | JSON text |
| NACK_JSON | 0x03 | device → host | JSON text |
| SENSOR_NOTIFY | 0x04 | device → host | `sensor_notify_payload_t` |
| STATUS_NOTIFY | 0x05 | device → host | JSON text |
| OTA_BEGIN | 0x10 | host → device | `ota_begin_payload_t` (116 bytes) |
| OTA_DATA | 0x11 | host → device | raw image bytes |
| OTA_END | 0x12 | host → device | `ota_end_payload_t` (8 bytes) |
| OTA_ABORT | 0x13 | host → device | none |
| OTA_PROGRESS | 0x14 | device → host | `ota_progress_payload_t` (16 bytes) |
| OTA_RESULT | 0x15 | device → host | `ota_end_payload_t` (8 bytes) |
| OTA_QUERY | 0x16 | host → device | none |
| OTA_INFO | 0x17 | device → host | `ota_info_payload_t` (32 bytes) |

`ota_begin_payload_t`:

```
0   u32 image_size     bytes, 64 .. 98304 (FLASH_SLOT_B_SIZE)
4   u32 image_crc32    CRC-32 of the whole image
8   u32 version        0x00MMmmpp (major, minor, patch)
12  u32 build_id       free-form
16  u16 hardware_id    must equal APP_HARDWARE_ID (0x0050)
18  u16 reserved       zero
20  32  image_sha256   SHA-256 of the image bytes
52  64  signature      Ed25519 over ota_signature_blob_t (see below)
```

The signature is mandatory: an all-zero signature is rejected with
`reason=9 (bad_signature)`. The signed blob binds the digest to the fields the
bootloader acts on:

```
0  32  image_sha256
32  u32 image_size
36  u32 version
40  u32 build_id
44  u16 hardware_id
46  u16 reserved = 0
```

`ota_info_payload_t` (answer to `OTA_QUERY`, sent after a reset or reconnect):

```
0   u8  state           ota_state_t
1   u8  reason          ota_reason_t
2   u16 reserved
4   u32 received        contiguous valid prefix that survives a reset
8   u32 total           announced image size
12  u32 image_crc32
16  u32 version
20  u32 chunk_size      resume granularity (8192 bytes)
24  u32 chunk_count     number of verified chunks
28  u16 hardware_id
30  u16 reserved2
```

`ota_progress_payload_t`:

```
0  u8  state          ota_state_t
1  u8  reason         ota_reason_t
2  u16 reserved
4  u32 received
8  u32 total
12 u32 crc32          running CRC-32 of accepted bytes
```

### 5.2 Transfer sequence

```
host                                    device
QUERY                                  -> INFO (state, received, chunk_count)
BEGIN (size, crc, version, hw, sha, sig) ->
                                        if manifest matches a persisted
                                        partial: verify chunk CRCs, report
                                        progress(state=RECEIVING, received)
                                        else: restart at 0
                                        progress(state=RECEIVING)
DATA offset=received                   ->
DATA offset=received+512               ->
...                                    progress/record every 8 KB chunk
DATA offset=N-512                      ->
END (image_size, crc)                  ->
                                        progress(state=READY_TO_BOOT)
                                        reads back slot B, checks CRC and SHA
                                        writes metadata (READY_TO_BOOT)
                                        <-- OTA_RESULT
                                        resets after 500 ms
```

The device verifies, in this order: size range and hardware id, monotonic
version, signature presence, per-frame CRC, contiguous offsets, final stream
CRC, SHA-256 of the flash content, and finally the bootloader verifies the
Ed25519 signature before slot A is touched. Any failure produces an
`OTA_PROGRESS` with `state=ERROR` and the reason code.

Resume rules:

- metadata is persisted at every 8 KB chunk boundary and on timeout/abort;
- each chunk CRC is stored, so a reset keeps only the longest prefix whose
  chunk records still match slot B;
- a manifest change (size/CRC/version/build/hardware/SHA/signature) discards
  the partial transfer and restarts at offset 0;
- `OTA_QUERY` reports the chunk-aligned offset, never a partially written
  chunk, so the host always resumes at an offset the device accepts.

### 5.3 State machine

```
IDLE --BEGIN--> RECEIVING --END--> VERIFYING --ok--> READY_TO_BOOT
  ^                 |                  |
  |                 +--- error/abort ---+--> ERROR
  |                                        |
  +--- (boot: slot A valid) <--------------+
```

Bootloader side:

```
IDLE / ERROR / RECEIVING / INSTALLED
    if slot A valid -> boot A (boot_attempts incremented; app confirms)
    if invalid and backup valid -> restore BACKUP into A, boot A
    else stay in bootloader

READY_TO_BOOT / INSTALLING
    validate slot B (size, vector table, CRC, SHA-256, Ed25519)
        fail -> ERROR, boot slot A if valid, else stay
        ok   -> snapshot slot A to BACKUP (first attempt only)
                attempts++, state=INSTALLING, erase slot A, copy B->A
                verify slot A CRC
                    ok   -> INSTALLED, attempts=0, boot A
                    fail -> stay INSTALLING, retry next boot (max 3)
```

Rollback: the bootloader increments `boot_attempts` on every jump to slot A.
The application calls `ota_service_confirm_boot()` after a 3-second healthy
grace period and clears the counter. If three consecutive boots end before
confirmation, `boot_policy_evaluate()` returns `ROLLBACK`, the BACKUP slot is
copied back into slot A and the attempt counter is cleared. `boot_attempts` is
persisted, so a reset loop cannot hide a broken image.

Reason codes: 0 none, 1 bad_state, 2 bad_size, 3 bad_crc, 4 out_of_order,
5 flash_error, 6 timeout, 7 aborted, 8 bad_version, 9 bad_signature.

Rules that keep the old image bootable:

- slot A is erased only after slot B has been fully validated,
- the running image is snapshotted into BACKUP before the first write to A,
- a failed or interrupted copy leaves slot B intact and state `INSTALLING`,
  which is retried on the next reset,
- after `BOOT_MAX_INSTALL_ATTEMPTS` (3) the state becomes `ERROR`; the
  bootloader then boots slot A if it still validates,
- a version lower than the running version is rejected both in the
  application (`ota_receiver_begin`) and in the bootloader,
- a signed image whose Ed25519 check fails is never copied into slot A.

### 5.4 Persisted records

Both metadata and WiFi credentials use `record_store`: two alternating 8 KB
pages, one record per page.

```
offset  size  field
0       4     magic "REC1" (0x52454331)
4       4     sequence (higher wins)
8       4     payload_len
12      4     payload_crc32
16      N     payload
```

Writing erases the page that does not hold the newest valid record, so a torn
write cannot destroy the last known-good copy. `record_store_load` picks the
valid record with the highest sequence. If both pages fail their magic,
length or CRC check (for example after a first-ever torn write), the load
returns `-1` and the caller falls back to safe defaults: `ota_metadata_default`
for the bootloader/OTA state and an unprovisioned (empty) WiFi config. The
host tests cover torn writes, erase faults, corrupting the newest record and
the both-pages-invalid fallback.

OTA metadata payload (`ota_metadata_t`, 528 bytes, fields `u32` unless noted):

| Field | Meaning |
| --- | --- |
| magic | `0x4F4D4554` ("OMET") |
| layout_version | 2 |
| state | `ota_state_t` |
| image_size | bytes in slot B |
| image_crc32 | CRC of the staged image |
| image_version | `0x00MMmmpp` |
| install_attempts | copy retry counter |
| boot_attempts | consecutive boots without app confirmation |
| boot_slot | `FLASH_SLOT_A_START` |
| previous_version | version running when the download started |
| received_bytes | contiguous prefix written to slot B |
| partial_crc32 | raw CRC accumulator for that prefix |
| build_id | free-form build identifier |
| hardware_id | must match `APP_HARDWARE_ID` |
| chunk_size | resume granularity (8192) |
| chunk_count | number of verified chunks |
| chunk_valid | bitmask of chunks re-verified after a reset |
| backup_valid | BACKUP snapshot completed and read back |
| backup_size / backup_crc32 / backup_version | snapshot descriptor |
| running_size / running_crc32 / running_version | image currently in slot A |
| image_sha256[32] | SHA-256 of the staged image |
| image_signature[64] | Ed25519 signature of the staged image |
| backup_sha256[32] / backup_signature[64] | snapshot authentication |
| running_sha256[32] / running_signature[64] | running image authentication |
| chunk_crc32[12] | CRC of each verified 8 KB chunk |
| reserved | zero |

WiFi record payload (`wifi_config_record_t`): `magic` "WCFG", `ssid_len`,
`password_len`, `auto_connect`, `reserved`, 32-byte SSID, 64-byte password.
Credentials are stored in plaintext on-chip flash, as is typical for ESP32
provisioning; this is not a secret vault.
